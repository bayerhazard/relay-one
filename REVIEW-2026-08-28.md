## Details

### H1 🟠 DB-Lock während Datei-I/O (Anhang-Read + base64)
- **Dateien:** `server/src/api/messages.rs:363-380` (`fetch_message_body`), `:1010-1024` + `:1033-1052` (`fetch_attachment_content`), Helper `attachment_inline_content` `:960-983`.
- **Problem:** `with_db` hält den **globalen** SQLite-Lock für die gesamte Closure. Innerhalb derselben Closure wird `std::fs::read(&abs)` (blockierend) + `base64::encode` ausgeführt. Ein 20-MB-Anhang hält den Lock für die Dauer von Read + base64 (~27 MB String) — **alle** anderen DB-Operationen (API + Sync-Loop) blockieren.
- **Reproduktion:** Mail mit großem Anhang öffnen, während parallel ein Sync-Zyklus oder eine andere API-Anfrage läuft → spürbare Verzögerung.
- **Fix:** Pfad (DB) im Lock lesen, Lock freigeben, Datei-Read + base64 **außerhalb** des Locks. `fetch_message_body`: Attachment-Metadaten + `disk_path` im Lock sammeln, dann die Reads sequenziell nach dem Lock. Gleiche Umstellung in `fetch_attachment_content`.
- **Test:** Regressionstest, der prüft, dass `attachment_inline_content`/die Body-Fetch-Pfade den Lock nicht während `fs::read` halten (z. B. Mock/Spion auf Lock-Dauer, oder Refactor-Unit-Test auf die neue Trennung).
- **Effort:** mittel (~1 h). Hot-Path, hoher Nutzen.
### H2 🟠 Reply-All enthält eigene Adresse (+ offene Reply-All-Issues)
- **Datei:** `web/src/routes/+page.svelte:1796` (`doHandleReply`).
- **Problem:** `replyTo = replyAll ? extractEmails(from, to, cc).join(", ") : …`. `extractEmails` (format.ts:53) filtert **nicht** die eigene Adresse. Bei „An alle antworten" auf eine Mail, die an mich + andere ging, landet meine eigene `sender_email` im Verteiler. Offenes High-Issue (BACKLOG 2026-08-18).
- **Fix:** Eigene Adresse des aktiven Kontos herausfiltern: `const own = (selectedAccount?.sender_email ?? "").toLowerCase();` und `.filter(e => e.toLowerCase() !== own)`. `selectedAccount` ist bereits `$derived` (Zeile 237) verfügbar.
- **Zu I4 („ein Block"/parse_to):** Der Send-Pfad splittet korrekt (`+page.svelte:2115-2123` `data.to.split(",")`). Restrisiko nur bei Display-Namen mit Komma (z. B. „Doe, John <j@x.com>") — `extractEmail` würde „Doe" als Adresse werten. Edge-Case, separat dokumentieren.
- **Test:** Vitest für `doHandleReply`-Logik (eigene Adresse wird gefiltert, Absender bleibt, CC bleibt) — ggf. `extractEmails` um eine `exclude`-Option erweitern und unit-testen.
- **Effort:** klein (~20 min).
### H3 🟠 Auth nur via Envoy-Sidecar, Public-Host keyless (by design)
- **Datei:** `server/src/api/mod.rs` (`relay_key_guard`).
- **Status:** Bewusstes Design (v26.09.92): API-Key-Guard deaktiviert, Zugriffsschutz liegt am Olares-Entrance (`authLevel: internal`, VPN). Live bestätigt: `/api/v1/accounts` + `/api/v1/messages` liefern 200 **ohne** Key (Cluster-/Entrance-Vantage-Point).
- **Residual-Risiko:** `relay_key_guard` lässt Public-Host-Requests (Host mit Punkt, z. B. `mail.aimighty.olares.de`) **keyless** durch — entweder via `RELAY_TRUSTED_HOST_SUFFIX`-Match oder (falls Env-Var unset) Legacy-Allow. Die App hat damit **keine** eigene Auth-Ebene; der Sidecar ist Single-Point-of-Failure für Auth.
- **Empfehlung (kein Code-Bruch):** (1) `RELAY_TRUSTED_HOST_SUFFIX` im Chart auf die Entrance-Domain setzen (Host-Spoofing-Schutz, CR-05). (2) Dokumentieren, dass der Sidecar zwingend ist. (3) Optional: für Public-Host-Requests ebenfalls einen Key verlangen (Frontend schickt ihn) — nur wenn Defense-in-Depth gewünscht.
- **Kein automatischer Fix** (Design-Entscheidung). Wird im Fix-Plan als „verifizieren + Chart-Env" geführt.
### M1 🟡 AI-Semaphore ohne Acquire-Timeout
- **Datei:** `server/src/ai/client.rs:95,126` (`acquire_owned().await` ohne Timeout).
- **Problem:** `Semaphore(1)` serialisiert LLM-Calls. Ein langsamer (nicht fehlerhafter) LLM hält den Permit ~120 s (reqwest-Timeout); eine Warteschlange langsamer Calls lässt User-Requests **unbegrenzt** warten. Circuit-Breaker hilft nur bei *Fehlern*, nicht bei *Langsamkeit*.
- **Fix:** `tokio::time::timeout(Duration::from_secs(30), self.semaphore.clone().acquire_owned())` → bei Timeout „busy"-Fehler (503). Bounded User-Wait.
- **Test:** Unit-Test: Semaphore voll halten, acquire mit Timeout → erwartet Timeout-Fehler statt Block.
- **Effort:** klein.
### M2 🟡 `open-url` ohne URL-Schema-Validierung
- **Datei:** `web/src/routes/+page.svelte:79-83` (Message-Handler) + injiziertes `linkScript` `:1255` (`postMessage(...,'*')`).
- **Problem:** `window.open(data.url, "_blank")` ohne Schema-Check. Eine bösartige Mail kann `{type:'open-url', url:'data:text/html,<…>'}` posten → Parent öffnet eine `data:`-URL in neuem Tab (Phishing-Seite). Kein Same-Origin-Datenleak (iframe ist sandboxed, opaque Origin), aber Phishing-Vektore bleibt.
- **Fix:** Schema validieren — nur `http:`/`https:` erlauben (via `new URL(url)` + `protocol`-Check). `postMessage`-Target auf `window.location.origin` statt `'*'` (falls iframe same-Origin wäre; hier sandboxed → `'*'` bleibt, Parent-Check ist der Schutz).
- **Test:** Vitest: `data:`/`javascript:`/`file:` URLs werden verworfen, `https:` erlaubt.
- **Effort:** klein.
### M3 🟡 Kein DB-Schema-Versioning (CR-11, offen)
- **Datei:** `server/src/cache/db.rs` (Schema via `CREATE TABLE IF NOT EXISTS` / `CREATE INDEX IF NOT EXISTS`, kein `PRAGMA user_version`).
- **Problem:** Schema-Evolution ist ad-hoc. Neue Spalten/Tabellen werden idempotent angelegt, aber es gibt keine Migration-Historie — bei bestehenden DBs mit geänderter Struktur ist das Verhalten nicht deterministisch. Risiko bei künftigen Breaking-Changes.
- **Fix (strukturell):** `PRAGMA user_version` einführen + sequentielle Migrationsfunktion (jeder Schritt idempotent). Kein akuter Bug — Backlog.
- **Effort:** groß (strukturell). Nicht in Stage D.
### M4 🟡 `/health` ist ein Stub
- **Datei:** `server/src/api/health.rs` (`health()` liefert immer `{"status":"ok"}`).
- **Problem:** Keine Prüfung von DB-Verbindung, IMAP-Status oder AI-Verfügbarkeit. Der Health-Check meldet „ok", auch wenn die App faktisch defekt ist (z. B. DB-Lock, alle IMAP getrennt). Für den Olares-Entrance (Liveness „Prozess läuft") ausreichend, aber kein Readiness-Signal.
- **Fix:** `/health` = Liveness (Prozess), optional `/ready` = Readiness (DB `SELECT 1` + mind. 1 IMAP verbunden). Oder `/health` prüft DB-Reachability (billig).
- **Test:** Unit-Test für den neuen Readiness-Pfad.
- **Effort:** klein.
### M5 🟡 Sync pro Account sequenziell
- **Datei:** `server/src/sync/scheduler.rs:751-844` (`do_sync_cycle`): Health-Ping (5 s) + `idle_wait` (20 s) **pro Account sequenziell** (`.await` in `for`-Loop).
- **Problem:** Zyklus-Dauer skaliert linear mit Konten-Anzahl. Bei N Konten: ~N × (Ping + IDLE + Sync). Bei 2 Konten ~50 s Worst-Case — akzeptabel, aber bei mehr Konten spürbar.
- **Fix (Skalierung):** Per-Account-Sync via `tokio::join!`/`futures::stream::buffer_unordered` parallelisieren (mit begrenzter Parallelität). Kein Bug — Skalierungs-Verbesserung.
- **Effort:** mittel. Backlog (aktuell 2 Konten, kein Schmerz).
### M6 🟡 64 MB Body-Limit + base64-Inlining
- **Dateien:** `server/src/main.rs` (`DefaultBodyLimit` 64 MB), `server/src/api/messages.rs` (base64-Inlining in JSON-Antworten).
- **Problem:** Große Anhänge werden als base64 in JSON inlined (+33 % Größe) → Memory-Spike + große Responses. Geteiltes Risiko mit H1 (Lock während Read).
- **Fix:** Teilweise via H1 (Lock trennen). Optional: Streaming/Chunking für sehr große Anhänge, oder Inlining-Größen-Limit (darüber nur Metadaten + separater Download-Endpunkt). Backlog.
- **Effort:** mittel/groß.
